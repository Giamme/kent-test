# Test Gate

A test is code someone maintains for as long as it exists. It earns that cost
only when it protects behavior a caller or user depends on, fails on a credible
regression, and is not already caught by another test. The common failure is
the opposite: a test for every function touched, assertions that restate the
implementation, and no evidence the test can ever fail. This skill is the check
before a test lands.

Apply it in proportion. Adding one row to a well-shaped table test is a
ten-second thought. A new test file, a regression test, or a review of someone's
tests deserves the full pass.

## 1. Learn how this repo tests

Before writing anything:

- Read the root and nearby `CLAUDE.md`, `AGENTS.md`, or contributing docs for
  test conventions and commands.
- Check the manifests: `package.json` scripts and workspaces, the `Cargo.toml`
  workspace, `pyproject.toml`, a `Makefile`, and so on.
- Read the existing tests closest to the code: their helpers, fixtures, naming,
  and which entry point they use to reach the code.
- Find the narrowest command that runs only the tests you touch (one file or a
  name filter). Avoid full suites and slow end-to-end runs unless the contract
  only lives there.

## 2. The gate

Answer four questions before adding a test. If one has no answer, do not add
the test yet.

1. **What does it protect?** Name the observable behavior, invariant, or
   contract: something a caller, user, file format, or protocol relies on.
   "The function works" is not an answer.
2. **What regression makes it fail?** Describe a plausible change a real
   developer might make that breaks that behavior. If you cannot, the test
   protects nothing.
3. **Why does existing coverage not catch it?** Search every test file for the
   symbol and the behavior, not just the sibling test file. Code is often
   covered through a caller: a helper through a component test, a validator
   through the storage layer, a template through the validator it must pass.
   Each contract needs one primary test at the strongest boundary that can
   observe it; a second layer is justified only by a risk the first cannot
   reach. If a table test or shared fixture already exists, add a row rather
   than a near-duplicate test.
4. **Does it need a seam production does not?** If the test only works by
   exporting something private, adding a flag or injection hook, or widening
   visibility, test through the real entry point instead. Language-level test
   access that changes nothing production exposes, such as a Rust `mod tests`
   inside the module, is not a seam.

"Nothing to add" is a legitimate outcome. When existing tests already protect
the behavior, name them (file and test) and stop, or close the specific gap you
found. Do not manufacture tests to satisfy a request for "more tests"; tell the
user what is already covered and what, if anything, was missing.

## 3. Junk patterns

Check every new or changed test against this list. A match fails the gate
unless the test independently guards a real contract (see section 6).

- **No assertion**: runs the code and checks nothing, or only that it did not
  throw when throwing was never plausible.
- **Self-comparison**: the expected value comes from the code under test, such
  as `expect(f(x)).toEqual(f(x))` or a fixture generated by running the helper
  being tested. Write expected values by hand.
- **Copied inventory**: re-listing constants, template contents, fixture data,
  export lists, or config the source already declares. It breaks on every
  intentional edit and catches nothing. Test the invariant the data must
  satisfy instead: it passes the real validator, keys are unique, references
  resolve.
- **Source grep**: reading source files and asserting a string or import is
  present. That asserts implementation text. The exception is when the string
  is the contract itself (a user-facing key, a path, wire bytes) and an
  internal rename would not break the test.
- **Call-shape tests**: asserting which internal function was called with
  which arguments when the outcome is observable at the boundary.
- **Duplicate coverage**: the same scenario is already asserted elsewhere at
  the same or a stronger boundary.
- **Mock that supplies the answer**: the mock returns the value the test then
  asserts, so the code under test is never really exercised. Also one generic
  mock standing in for several different dependencies.
- **Negative case that passes for the wrong reason**: a "rejects X" input that
  is invalid in several ways, so the test still passes if the X check is
  deleted. Start from a known-valid input, change exactly one thing per case,
  and include the positive control showing the valid input is accepted.
- **Name promises more than the input exercises**: "drops non-finite values"
  with only finite inputs; "retries on failure" where nothing fails.
- **Test-only production code**: exports, globals, wrappers, or branches that
  exist only because a test uses them.

## 4. Writing the test

- Test at the owning boundary, the entry point real callers use. A test that
  would break under a behavior-preserving refactor (renaming a private helper,
  reorganizing internals) is asserting implementation; move it outward.
- Hand-write expected values as literals.
- Cover variants of one contract with a table (`it.each`, a cases array, a
  loop), each row naming what it covers.
- Negative cases: one known-valid fixture, one mutation per case, plus the
  positive control. Test limits at the edge: accepted at the maximum, rejected
  one past it.
- Match the surrounding tests' helpers, style, and density.
- Run the narrowest command and confirm the new tests pass.

## 5. Regression tests must fail first

A regression test that never failed proves the mock, not the fix. For any test
that claims to catch a bug:

1. Write the test against the fixed code.
2. Temporarily restore the pre-fix behavior: stash the fix, check out the file
   from before the fix (`git show <fix>^:<path> > <path>`), or revert only the
   relevant lines.
3. Run the test and confirm it fails **for the intended reason**. Read the
   failure: a compile error or an unrelated exception does not count.
4. Restore the fix, confirm the test passes, and check `git status` and
   `git diff` so nothing from the temporary revert is left behind.
5. Report the observed failure message.

One regression test at the owning boundary covers the bug. Do not replay the
same scenario at every layer it passes through.

If you cannot reproduce the pre-fix failure (history unavailable, a rebuild too
costly), say so plainly instead of implying the test was proven.

## 6. Reviewing tests

When reviewing someone's tests or existing ones, give each a verdict and a
reason:

- **keep**: name the contract and the regression it catches;
- **fix**: the contract is real but the assertion is weak, misnamed, or passes
  for the wrong reason;
- **merge**: fold it into an existing test or table, and say which;
- **drop**: name the existing proof that remains, or why no contract exists.

Judge a test by its assertions, not its name.

Do not over-prune. Keep tests that independently guard a public API, protocol
or wire format, persistence or migration, security, config defaults, documented
limits, user-facing text that is a contract, or ordering when order is
observable. "Looks like implementation", "static", and "slow" are not reasons
to delete on their own. If a test you would keep fails on the current code,
treat it as a possible product bug and investigate before changing the test.

## 7. Report

Finish with a short account:

- each test added or changed: what it protects and the regression it catches;
- for regression tests, the observed pre-fix failure;
- tests you considered and did not add (or dropped), with the coverage that
  makes them unnecessary;
- the commands you ran and their results.

A few lines per test, not an essay.
